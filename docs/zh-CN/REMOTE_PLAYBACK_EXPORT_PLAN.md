# 远程播放、视频导出与云端访问开发流程

## 1. 文档目的

本文记录 TeslaBox 录像播放从局域网原画回放演进到低带宽远程访问的开发顺序、接口边界和验收条件，避免把播放器布局、转码、导出、WebRTC 和云端控制混成一个不可验证的大改动。

当前网页的多路播放会分别请求每个摄像头的原始 MP4。该方式适合 AP 或高速局域网，但远程播放消耗的是多路原始码率之和。三路、四路和六路远程播放的最终形态必须由 TeslaBox 合成为一条低码率视频后再发送。

## 2. 已确认需求

### 2.1 播放画质

- 支持自动、流畅、标准、高清和原画。
- 手动画质保持到用户重新选择，浏览器刷新后仍然生效。
- 自动画质综合传输路径、实测吞吐、RTT、缓冲时长、卡顿次数和设备转码负载判断。
- 降档要快，升档必须经过稳定观察，避免画质反复跳动。
- 在低码率转码尚未实现前，不向用户伪装已经存在的画质档位。

建议初始档位如下，最终数值以 ROCK 3A 真机测试为准：

| 档位 | 建议输出 | 目标码率 |
| --- | --- | --- |
| 流畅 | 480p | 约 1.5 Mbps |
| 标准 | 720p | 约 3 Mbps |
| 高清 | 1080p | 约 8 Mbps |
| 原画 | 单路源分辨率 | CQP 高质量重新编码 |
| 原画 | 原始 MP4 | 不重新编码 |

### 2.2 播放布局

播放器支持以下模式：

| 模式 | 摄像头与布局 |
| --- | --- |
| 六路合成 | 左 B 柱、前视、右 B 柱、左翼子板、后视、右翼子板 |
| 四路合成 A | 左上前视、右上后视、左下左翼子板、右下右翼子板 |
| 四路合成 B | 第一行前视；第二行右翼子板、后视、左翼子板 |
| 三路合成 | 第一行前视；第二行右翼子板、左翼子板 |
| 单视角 | 用户选择的一路摄像头 |

画面默认保持原始比例，不裁剪；比例不一致的区域用黑色填充。缺失视角显示占位提示，不能阻止其余视角播放。

### 2.3 自定义导出

- 用户可选择录像、开始位置、导出时长、摄像头、布局和画质。
- 跨越多个一分钟文件时按统一时间轴拼接。
- 最终只生成一个完整 MP4。
- 单路且无需时间修正的导出可优先尝试无损拼接；多路合成必须重新编码。
- 导出是异步任务，支持排队、进度、取消、重启清理和空间预估。

不同视角存在 1～2 帧时差时，以 MP4 的 PTS/DTS 和首个可解码帧建立共同时间轴，以前视摄像头作为主时钟。提前的视角裁帧，延后的视角补黑帧或首帧，之后统一为固定帧率。额外提供按摄像头保存的帧偏移校准值，不依赖跨视角画面相似度猜测。

### 2.4 云端控制与 WebRTC

TeslaBox 主动向云端建立加密长连接，用于设备心跳、状态、WebRTC 信令和受限的业务指令。控制通道不承载六路原始录像，也不允许执行任意 Shell 命令。

媒体路径按以下顺序选择：

1. AP 或同一局域网直接访问。
2. WebRTC 通过 STUN 建立 P2P。
3. P2P 失败后通过 TURN 中继。

一个域名访问采用“每台设备固定域名 + 分流 DNS”：AP/局域网把同一设备域名解析到 TeslaBox，本地之外解析到云端入口。浏览器地址不变，ICE 协商决定媒体实际走局域网、P2P 还是 TURN。每台设备必须使用独立证书，不能把同一张通配符私钥复制到所有设备。

## 3. 分阶段开发流程

### 阶段 A：播放器布局与观测能力

- [x] 增加六路、四路 A、四路 B、三路和单视角切换。
- [x] 多路模式只加载布局实际使用的摄像头。
- [x] 保存用户上次选择的布局和画质偏好。
- [x] 展示当前网络路径、浏览器网络信息、实际媒体吞吐和缓冲时长（浏览器侧第一版）。
- [x] 记录主播放轨道的卡顿次数，为自动画质提供输入。

验收条件：

- 三路模式只有三个视频内容请求，四路模式只有四个。
- 切换布局后播放位置不回到开头。
- 手机端和桌面端布局均无溢出，缺失摄像头有明确提示。
- 页面明确区分浏览器估算带宽和实际媒体吞吐。

### 阶段 B：ROCK 3A 媒体能力基准

- [x] 采集真实 Tesla MP4 的编码、分辨率、帧率和容器时间基线。
- [x] 验证 FFmpeg 是否能调用 Rockchip MPP 解码、编码和 RGA 缩放。
- [x] 分别测试单路、三路、四路和六路解码加一路编码。
- [x] 记录 CPU、内存、温度、帧率和长时间稳定性；功耗仍需配合外部电流表补充同场数据。

验收条件：至少连续运行 30 分钟，不发生持续降频、内存增长或服务异常。未通过前不得默认开启板端多路转码。

2026-07-20 板端基线：Debian 11、内核 `5.10.160teslabox1` 已安装独立媒体工具链到 `/opt/teslabox/media`。使用 1280×720、30 FPS、5 秒合成样本验证 `h264_rkmpp` 编码约为 3.95 倍速；使用 DRM PRIME 硬件帧完成 `h264_rkmpp` 解码和 `scale_rkrga` 640×360 缩放约为 15.2 倍速，峰值内存约 20 MB。该结果只证明单路硬件链路可用，不能替代真实 Tesla 文件、多路并发和 30 分钟稳定性验收。

代码已提供 `/api/v1/media/capabilities` 和 `/api/v1/videos/{id}/metadata`，用于从当前只读快照采集真实文件参数。下一步部署新版后抽取六个视角的样本，并增加数据包级 PTS/DTS 与关键帧间隔汇总。

2026-07-20 真实录像基线：前视为 2896×1876、约 10.5 Mbps，其余五路为 1448×938、各约 5.3 Mbps；全部为 H.264 High、约 36 FPS、单段约 60 秒。原始六路总码率接近 37 Mbps。

第一版连续 `overlay_rkrga` 合成的六路速度只有 0.561 倍实时。改为 MPP 解码、RGA 缩放、缩小后的 NV12 一次性 `xstack`、MPP 编码后，1280×720 六路 30 FPS 达到 1.20 倍实时，24 FPS 达到 1.51 倍，20 FPS 达到 1.56 倍；三路 30 FPS 为 2.02 倍，四路 30 FPS 为 1.64 倍。测试峰值温度 61.7°C、进程内存约 35 MB。该结果允许进入实时合成接口开发，但仍需完成 30 分钟稳定性验收。

2026-07-20 六路标准画质真实 HTTP 连续播放 30 分钟通过：180 个 10 秒采样点内 FFmpeg 最多 1 个，活跃时平均 CPU 126.2%，峰值 CPU 164%，FFmpeg 最大 RSS 39.9 MiB，服务内存峰值 641.6 MiB 且可回落至 48.3 MiB，最高温度 71.7°C，服务重启 0 次，压测窗口内新增 loop I/O、段错误和 OOM 记录均为 0。关闭播放器后 FFmpeg 归零、服务内存回落至约 64 MiB。

### 阶段 C：低码率合成与自动画质

- [ ] 建立统一布局描述，供网页预览和板端合成共用。
- [x] 生成流畅、标准、高清多档实时合成输出。
- [ ] 录像回放采用支持分段和切档的 HLS/CMAF 或等价方案。
- [ ] 自动画质实现快速降档、延迟升档和手动锁定。
- [x] 转码加载失败或播放时钟连续 8 秒不前进时，按高清、标准、流畅、单路原画逐级回退；临时降级不覆盖用户保存的画质偏好。
- [x] 自动画质采用安全初始档位：多路布局默认标准合成，单路布局默认原画；手动选择仍保持用户锁定的档位。

### 阶段 D：自定义导出

- [x] `POST /api/v1/exports` 创建导出任务。
- [x] `GET /api/v1/exports/{id}` 查询状态和进度。
- [x] `DELETE /api/v1/exports/{id}` 取消任务。
- [x] `GET /api/v1/exports/{id}/download` 下载结果。
- [x] 默认只允许一个任务执行，并设置有界队列。
- [x] 使用临时文件生成，完成后原子重命名；失败或重启后清理遗留文件。

第一版默认允许从当前完整录像的任意位置导出最长 2 分钟，导出视角与播放器保持一致：六路合成、四路合成 A、四路合成 B、三路合成和任一单路视角。单任务最多接受 12 个跨分钟输入片段；超过时要求用户缩短范围，避免 ROCK 3A 在长时间导出时打开过多解码器。剪辑导出默认只提供高保真合成：维持 30 FPS 和现有布局像素尺寸，空间预留按 64 Mbps 的保守上界估算。2026-07-30 使用同一段真实 Tesla MP4 重复构成六路，并固定多路布局的 A/B 结果显示，`h264_rkmpp` 最终编码会产生跨格一致的水平残块，而仅将最终编码器改为 `hevc_rkmpp` 后残块消失。使用 MPP 硬件解码、RGA 缩放和 HEVC 硬编的三秒六路样本耗时 11 秒（约 0.44 倍速）、文件约 2.1 MB（约 5.6 Mbps）、温度从 33.1°C 升至 36.1°C，画面无残块；因此多路高保真导出固定为该硬件流水线和低 QP CQP（QP 16–20），并写入 `hvc1` MP4 标记。它是下载文件，不改变网页在线播放的 H.264 路径。用户需要用支持 HEVC 的本地播放器播放多路高保真 MP4。H.264 的全 I 帧样本同样无残块，但约 142 Mbps、三秒约 53 MB，不适合作为默认兼容格式。单路高保真和单路原画保持既有 H.264 RKMPP 路径；单路原画因为跨分钟和精确裁剪需要统一时间轴，仍使用 CQP 高质量重新编码，而不是简单复制码流。多路无法在 ROCK 3A 上生成一个与六路源文件像素完全相同的 MP4：网页原画是浏览器分别解码六个原始文件，而不是板端合成后再编码。为此，“多路原画”导出按完整分钟无转码打包原始 MP4、清单和离线 `player.html`，解压后可在电脑浏览器同步查看原画。任务按录像绝对时间裁剪跨分钟片段；某一路比公共时间轴晚开始或中间缺少短片段时，以最近可用帧补齐，再统一帧率并合成为一个 MP4。创建任务后会持有对应只读快照租约，取消排队任务立即释放，运行中的任务则等 FFmpeg 真正退出后释放；主服务退出也会等待导出工作进程完成回收，避免与快照清理并发。

多路导出已改为复用播放器的布局比例计算，不再把 Tesla 约 1.54:1 的源画面强制补边进固定 16:9 格子。“1080 高度”表示六路、四路 A 的内容画布高为 1080 像素；四路 B、三路会为保持布局比例使用更高的画布。内容画布分别为六路 2502×1080、四路 A 1668×1080、四路 B 1248×1620、三路 1112×1440。高保真导出只会在最终画布最右侧和最下侧补充不足 16 像素的黑边，实际编码画布依次为 2512×1088、1680×1088、1248×1632、1120×1440；这样让 RKMPP 接收对齐帧缓冲，同时不缩放任何源画面。每个格子只做接近源比例的极小幅缩放，不再主动添加黑边。

## 4. 自动画质判定原则

自动模式不能只读取 `navigator.connection`。该接口只作为提示，还要使用真实媒体请求的下载字节和耗时计算吞吐，并持续观察播放器缓冲区。

- 缓冲不足或连续卡顿时立即降一档。
- 实测吞吐低于当前目标码率的 1.25 倍时禁止升档。
- 实测吞吐高于下一档目标码率的 1.5 倍并稳定 20～30 秒后才允许升档。
- TURN、DERP 或 Peer Relay 路径默认从标准或流畅档开始。
- AP 和局域网可以优先高清，但不能忽略设备转码负载。

## 5. 安全和资源边界

- 云端指令使用明确的类型和参数白名单，不提供远程 Shell。
- 导出队列、转码进程、临时空间和日志大小必须有上限。
- 所有后台任务都必须支持取消和超时。
- 外接数据盘空间不足时优先保障 Tesla 写入，不启动新导出任务。
- TURN 只作为兜底，必须配置用户鉴权、流量限制和过期凭证。

## 6. 当前执行位置

当前已完成阶段 B 的真实 HTTP 30 分钟稳定性验收、阶段 C 的实时多档合成、失败自动降级和安全初始档位，以及阶段 D 的自定义导出第一版。网页可以选择起点、时长、与播放器一致的视角布局和导出画质，查看排队/进度、取消任务并下载单个 MP4；开始导出时会主动停止当前播放器媒体请求，后台还会串行化实时合成与导出，避免 MPP/RGA 并发争用。下一步先在 ROCK 3A 上用真实两分钟以上录像验证单路原画、三路、四路和六路 1080p 跨分钟导出、取消和 FFmpeg 回收，再继续基于吞吐、RTT、缓冲和负载动态升降档；数据包级时间戳汇总和外部电流表功耗记录仍待补充。
