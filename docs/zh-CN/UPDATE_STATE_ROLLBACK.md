## 事务保护内容

事务配对保存 `/usr/local/bin/teslabox` 和 `TESLABOX_EXPORT_STATE`（默认 `/var/lib/teslabox-system/export-state.json`）。这是已确认的 0.1.31 → 0.2 导出格式不兼容点，**不是全盘快照或任意未来状态迁移的通用保证**。新增不兼容状态时必须扩展目标清单和验证。

1. 锁定安装，停止主程序，核对进程退出；状态路径须与主程序实际环境一致。
2. 保存原程序和状态、权限及 SHA-256；原状态不存在时记录不存在。备份和事务记录完成文件及目录同步后才替换程序。
3. 候选验证期间，HTTP 只放行健康检查；暂停导出、上传、缓存清理和本机自动化。直到事务提交且安装锁释放后才允许新任务运行，避免失败回滚撤销用户新操作或引用已删除成品。
4. 失败时停止候选，保存失败现场，先恢复旧状态，最后恢复旧程序，再启动并验证旧服务。恢复失败不报告成功。
5. 未提交事务在下一次 systemd 启动前恢复。恢复中再次中断可继续；未知并发写入、损坏备份、路径变化会拒绝覆盖并保留现场。

忙锁不代表启动授权。候选完整替换、实际摘要核对并写入 `ready` 后，或者恢复全部完成并写入 `rolled_back` 后，助手才临时监听私有目录内的 Unix socket，0600 权限，校验 SO_PEERCRED，限制报文长度和 15 秒收发时间，只提供一次绑定 journal 摘要的许可。守卫再次核对记录和程序/状态快照。`prepared`、替换前 `activating`、`restoring`、缺失/损坏记录和首次 bootstrap 都不提供许可。无服务的残留 socket 不构成许可；仅在核对所有权、inode 且连接明确被拒绝后才清理，活动 socket 不删除。

并发的 `systemctl start` 若恰好到达安全许可窗口，可消费同一个安全启动意图；助手使用 `start` 而非 `restart`，不重复启动已获许可的实例。提交前还须核对 MainPID、`/proc/PID/exe` 与安装文件 inode，并对新候选校验健康响应的 `X-TeslaBox-Process`。回滚旧程序不要求新 header。缺失 journal 的准备失败路径先单次释放锁，再启动未被修改的原程序，此后不再进行本次安装写入。

所有新目录逐级建立并同步各父目录，已存在的目录也重新同步以覆盖上次 mkdir 后 fsync 失败的重试。目录同步失败向上传播，不以正常 mkdir 返回值代替耐久性证据。

恢复重试发现目标已等于原快照时，仍须重新同步目标父目录；原状态不存在也一样。原父目录从未存在时同步最近存在的祖先，不新建状态目录。这样覆盖恢复 rename/remove 成功但父目录同步失败的窗口；屏障未成功时不能写 `rolled_back` 或启动旧程序。

提交前先持久写入 `active/commit-pending` 隔离标记，再写 `committed`。若提交记录 rename 成功、目录同步失败，且候选停止也失败，标记仍阻止业务与下一次启动，不依赖故障后还能补写失败记录。后续安装也在归档 active 前拒绝覆盖隔离事务。`ready/activating/restoring` 加隔离标记仍可由启动守卫自动成对恢复；`rolled_back` 加标记会重新验证恢复屏障后清理。缺失/损坏记录、无效标记以及 `committed` 加标记则保留现场并拒绝自动启动，需维护者核对，不推断提交成功。

只有提交记录已经持久完成，才删除隔离标记。若删除成功但目录同步失败，当前运行中标记可能已不可见，新版可以在锁释放后放行；掉电后标记可能重新出现，启动守卫会拒绝启动。此时**程序与状态已经提交，不能再自动回滚**；助手明确报“已持久提交、隔离清理未确认，未执行回滚”，不宣称仍保持隔离或已经恢复旧版。正常回滚时只在所有目标屏障和 `rolled_back` 同步完成后清理标记，因此清理故障也不能让候选重新运行。

事务位于 `/var/lib/teslabox-system/update-backups/active`，上一轮终态归档到 `history-*`。`before-*`、`failed-*`、`transaction.json` 为 0600，目录为 0700。当前不自动删除故障证据，维护者应归档历史备份并留足空间；空间不足导致备份失败时不得替换程序。单程序上限 128 MiB，单导出状态上限 16 MiB。

原始录像、Gadget backing image、物理 USB 状态不做文件回滚；不能把磁盘文件恢复当作车机录像验收。升级期间应按现有要求进入维护窗口。NAS/缓存新增状态不回退为旧格式，旧版未消费的新数据留在原路径。

## 首次从旧助手迁移

这是一次独立维护引导，当前单二进制 OTA 清单**不会自动完成**。旧客户端先只收到新主程序时，新主程序会在状态构造器之前拒绝启动；旧助手可恢复旧程序，不会在该路径写入 v2。此行为是保护失败，不是升级成功。

发布端必须先固定新源码，构建新助手，再将以下内容及 SHA-256 纳入可信签名的引导发布物：

- `teslabox-update-helper`（ARM64），协议输出 `teslabox-paired-state-v1`；
- `deploy/scripts/bootstrap-update-rollback.py`；
- 对应源码版本与旧助手摘要、引导步骤。

**本源码不包含新的签名或产物摘要。** 摘要必须来自已验证签名的发布清单/维护者可信交付；与未知来源文件一起下载的 `.sha256` 自身不是认证。引导脚本校验输入摘要，但不替代发布清单签名验证。不改既有 OTA 信任公钥，不分发任何私钥。

原 Manifest v1 字段、签名载荷与旧客户端请求格式保持不变。保护能力声明嵌入主程序 ELF `.rodata`，由实际启动检查使用，随整个程序的已验签 SHA-256 绑定。助手使用同一份已核对摘要的字节解析 ELF，要求 `.rodata` 为可分配、不可写的 PROGBITS 节，恰好包含完整固定声明；文件尾部/可写段中的字符串不算。无声明的原 RC1 在停止、备份和执行前拒绝，不等启动后再用缺失 header 判断。声明是发布者认证的能力承诺，仍需源码审查和真实回归，不能证明任意签名者的代码正确。真正发布 ELF 是否保留声明还必须在构建后检查；合成 ELF 单测不能替代这项检查。

在确认停止录像和 CarPlay 的维护窗口，管理员先确认更新服务没有运行，再停止主服务。确认引导脚本的可信摘要后执行：

```sh
sudo systemctl stop teslabox.service
# 须将候选助手安全复制为 root 拥有、仅 root 可写的普通文件。
sudo python3 bootstrap-update-rollback.py \
  --helper /root/teslabox-update-helper.new \
  --sha256 '<可信签名清单中的新助手SHA-256>'
```

脚本要求主服务和更新助手均为 inactive/failed，不主动中断正在执行的安装。使用同一安装锁并拒绝已有未完成事务；固定检查旧助手摘要。输出路径固定，不接受远端提供的目标路径。

安装顺序：

1. 私有目录保存旧助手、已有同名 drop-in、权限和新旧摘要。`manifest.json` 为 0600，持久记录固定目标路径、原文件存在性、mode、备份名和 SHA-256；所有备份及元数据完全同步后才覆盖助手。掉电后不能依赖进程内的 `previous` 字典恢复。
2. 原子写入新助手 `/usr/local/libexec/teslabox-update-helper`（0755），同步落盘。
3. 写入更新服务 drop-in（0644），继承 `/etc/teslabox/teslabox.env`，超时改为 240 秒。
4. 最后写入主服务 drop-in（0644），增加 `ExecStartPre=... --recover`，不清除已有 ExecStartPre。
5. daemon-reload，并核对生效的启动守卫。主程序仍保持停止。

异常恢复顺序：先恢复/移除主服务 drop-in，再恢复更新服务 drop-in，最后恢复旧助手，再 daemon-reload；任一步恢复失败就报错并保留证据，不能继续覆盖。掉电时只有“新助手+旧守卫配置”或“新助手+新守卫配置”，不应出现旧助手配新守卫。原 unit 文件从未被引导脚本覆盖。

若引导中断但新助手已落盘，再次执行会因旧摘要不匹配而拒绝。维护者必须先核对私有备份和当前摘要，再显式指定已核实的 `--old-sha256`；不自动猜测或覆盖。

完成引导后可先启动旧主程序，确认仍可读取旧状态，再从原签名 OTA 通道安装新候选。或者在维护窗口用更新后的 `install-teslabox-update.sh <二进制> <版本号>`，它同样调用事务助手；原来传助手/unit 的位置参数已取消，旧调用会拒绝而不会安装。手动方式的摘要文件必须来自可信发布交付。

自定义导出状态只接受主服务和更新服务一致的 `TESLABOX_EXPORT_STATE`。优先放在共同的 EnvironmentFile；若只在主服务 drop-in 覆盖，必须同步更新服务，否则安装会拒绝。不要用符号链接或硬链接绕过状态路径保护。
